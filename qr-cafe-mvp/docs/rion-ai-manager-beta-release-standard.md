# Rion AI Manager 베타 공개 기준

상태: **AI 기능 구현 전 내부 기준 확정**

## 이 문서의 목적

Rion AI Manager 베타는 "덜 만든 기능을 먼저 공개"하는 단계가 아니다.

> 제한된 베타 매장이 실제로 사용해도 안전하고, 이해하기 쉽고, 운영자가 비용과 오류를 관리할 수 있는 완성된 기능 묶음을 검증하는 단계다.

따라서 이후 AI 개발은 이 문서의 공개 기준을 충족한 뒤에만 베타 매장에 제공한다.

## AI Manager가 하는 일

Rion AI Manager는 단순히 주문 통계를 다시 보여주는 기능이 아니다.

1. 주문과 운영 데이터를 살핀다.
2. 중요한 문제나 기회를 찾는다.
3. 확인된 숫자와 가능한 원인을 구분해 설명한다.
4. 점주가 먼저 검토할 개선안 **하나**를 제안한다.
5. 점주가 승인한 경우에만 제한된 실험으로 관리한다.
6. 결과를 확인해 채택, 종료, 추가 검토 중 하나로 정리한다.

AI는 점주 승인 없이 메뉴, 가격, 쿠폰, 포인트, 주문, 결제, 매장 설정을 바꾸지 않는다.

## 베타에서 공개할 완결된 흐름

베타 매장에는 아래 흐름 전체가 동작해야 한다.

```text
오늘의 AI 요약
→ 문제 또는 기회 확인
→ 근거와 제안 1개 확인
→ 점주 승인 또는 보류
→ 실험 진행
→ 효과 확인
→ 채택 / 종료 / 추가 검토
```

### 1. 오늘의 AI 요약

- 점주가 오늘 확인할 항목은 최대 3개로 제한한다.
- AI Brief는 베타 참여와 동시에 제공한다. 초기에는 주문 수·매출·상위 메뉴·취소 건수처럼 **현재 확인된 사실**과 데이터 수집 상태만 보여 준다.
- 정상일 때는 억지로 추천하지 않는다.
- 데이터가 부족하면 "아직 판단할 데이터가 부족합니다"라고 명확히 표시한다.
- 즉, 사실 요약은 처음부터 제공하고, 비교 분석과 개선 제안은 데이터가 쌓인 뒤에만 제공한다.

### 2. 문제·기회와 제안

각 AI 카드에는 아래 내용을 모두 표시한다.

- 무엇이 달라졌는지
- 근거가 되는 핵심 숫자 2~3개
- 확인된 사실
- AI의 추정 또는 원인 가능성
- 추천하는 행동 1개
- 분석 신뢰도
- 점주가 할 수 있는 다음 행동

AI는 알 수 없는 원인을 사실처럼 단정하지 않는다.

### 3. 점주 승인과 실험

- 점주가 승인하기 전에는 어떤 변경도 실행하지 않는다.
- 실험에는 문제, 가설, 변경 내용, 기간, 성공 기준, 주의할 부작용 지표를 기록한다.
- 한 번의 실험에서는 가능한 한 핵심 변경 하나만 다룬다.
- 실험은 중단하거나 되돌릴 수 있어야 한다.

### 4. 결과 확인

- 단순히 전보다 숫자가 높아졌다고 성공으로 판단하지 않는다.
- 같은 요일·시간대 등 가능한 비교 기준을 함께 사용한다.
- 데이터가 부족하거나 결과가 불명확하면 "추가 관찰"로 남긴다.
- 효과가 확인된 방식만 `STABLE` 상태로 관리한다.

## 시스템과 AI의 역할 분리

AI가 숫자를 직접 계산하거나 데이터베이스를 직접 수정하게 하지 않는다.

```text
주문·취소·품절·처리시간 데이터
→ 시스템의 고정 계산과 확인 규칙
→ 문제·기회 신호
→ AI가 이해하기 쉬운 설명과 제안 작성
→ 점주 승인
→ 서버가 실제 규칙을 다시 확인한 뒤 실행
```

이 원칙은 AI의 잘못된 계산, 근거 없는 단정, 권한 없는 변경을 막기 위한 것이다.

## 데이터와 개인정보 기준

- 분석 기준은 반드시 `Rion Order 주문 기준`이라고 표시한다.
- 고객 이름, 전화번호, 주소, 개별 주문 원문처럼 개인을 식별할 수 있는 정보는 AI 분석에 보내지 않는다.
- 매장별 주문 수, 매출 합계, 메뉴별 판매 수, 취소율, 처리시간 등 필요한 집계 데이터만 사용한다.
- 데이터가 적은 매장은 분석을 보류한다.

## OPS의 AI 사용량·비용 통제

OPS는 AI 기능을 단순히 조회하는 곳이 아니라, 안전하게 운영하는 통제 화면이어야 한다.

### OPS에서 반드시 확인할 항목

- 매장별 AI 호출 횟수
- 점주 계정별 AI 호출 횟수
- 기능별 호출 횟수: 오늘의 AI 요약, 개선 제안, 실험 결과 확인 등
- 일별·월별 실제 또는 추정 AI 비용
- 플랫폼 전체 누적 비용과 남은 예산
- 오류 호출, 실패율, 데이터 부족으로 분석하지 않은 비율
- 진행 중인 실험과 `STABLE` 항목 수

### OPS에서 반드시 제어할 항목

- 매장별 일·월 AI 사용 한도
- 점주 계정별 사용 한도
- 플랫폼 전체 일·월 예산 한도
- 기능별 사용 허용 여부
- 특정 매장 또는 특정 계정의 AI 기능 일시 중지
- 비용 또는 오류 기준을 넘었을 때 자동 중지
- 운영자가 다시 허용하기 전까지의 차단 상태

한도에 도달했을 때 점주 화면에는 어려운 오류 대신 아래처럼 안내한다.

> 현재 AI 분석 사용 한도에 도달했습니다. 다음 사용 가능 시점 또는 매장 관리자 안내를 확인해 주세요.

## 베타 공개 전 필수 점검

아래 항목 중 하나라도 빠져 있으면 베타 매장에 공개하지 않는다.

- [ ] 점주 화면에서 AI의 근거·추정·추천을 구분해 볼 수 있다.
- [ ] 데이터 부족 상태가 정상적으로 표시된다.
- [ ] 점주 승인 없이는 실제 변경이 실행되지 않는다.
- [ ] 실험을 중지하고 되돌릴 수 있다.
- [ ] 효과 검증 결과와 판단 근거가 남는다.
- [ ] AI 호출·비용·오류·한도를 OPS에서 확인할 수 있다.
- [ ] OPS가 매장·계정·기능별 AI 사용을 중지하거나 다시 허용할 수 있다.
- [ ] 개인정보를 제외한 최소 집계 데이터만 AI에 전달한다.
- [ ] AI 오류가 나도 주문, 결제, 매장 운영의 기존 기능은 계속 사용할 수 있다.
- [ ] 잘못된 추천, 데이터 부족, 한도 초과, 승인 취소, 실험 실패 사례를 사전 테스트했다.

## 구현 순서

모든 항목은 베타 공개 전에 완성되어야 하지만, 개발은 아래 순서로 진행한다.

1. 데이터 준비와 안전장치
2. AI 분석 결과를 저장하는 구조와 OPS 사용량·비용 통제
3. 점주용 AI 요약·개선 제안 화면
4. 승인·실험·중지·되돌리기 흐름
5. 결과 검증과 `STABLE` 상태
6. 베타 시나리오 테스트와 제한된 매장 공개

## 현재 Rion Order 준비 상태 점검

점검일: 2026-09-08

### 이미 준비된 기반

- 매장별 주문 일시, 주문 금액, 주문 수량, 매장/포장 구분, 주문 상태가 저장된다.
- 주문별 메뉴, 수량, 가격, 환불 수량이 저장된다.
- 취소 주문과 부분 환불을 구분할 수 있는 기반이 있다.
- 점주 통계 화면에서 매출, 주문 수, 객단가, 시간대별 주문, 인기 메뉴를 계산한다.
- 점주·직원·매장별 권한 확인과 OPS 운영자 권한 확인이 있다.
- OPS에 매장·구독·결제·문의의 기본 운영 현황이 있다.

따라서 AI가 사용할 수 있는 "매장별 주문 요약 데이터"는 새로 만들 필요 없이 현재 데이터를 바탕으로 준비할 수 있다.

### 베타 전에 새로 만들어야 하는 기반

- AI 분석 결과, 제안, 승인, 실험, 결과, `STABLE` 상태를 안전하게 저장하는 전용 구조
- AI 호출 1회마다 매장, 점주, 기능, 모델, 사용량, 비용, 성공/실패를 남기는 기록
- 매장별·점주별·플랫폼 전체의 일/월 한도와 차단 상태
- OPS에서 AI 사용량과 비용을 보고 중지·재허용하는 화면
- AI가 읽을 수 있는 집계 데이터 API. 고객 개인 정보와 주문 요청 메모는 제외한다.
- 주문 상태가 바뀐 정확한 시각을 남기는 이력. 이것이 있어야 주문 처리 지연을 신뢰성 있게 분석할 수 있다.
- 최근 동일 요일·시간대와 비교하는 기준 데이터와 데이터 충분성 판단 기준
- AI 오류, 시간 초과, 사용 한도 초과 때 기존 주문·통계 기능으로 안전하게 돌아가는 처리

### 현재 단계의 중요한 제한

현재 시스템에는 주문·메뉴 데이터는 있지만, 매장별 실제 데이터 기간과 주문량이 AI 분석에 충분한지는 별도 확인이 필요하다.

데이터가 충분하지 않은 매장은 베타 화면에서 억지로 추천을 만들지 않고 `DATA_INSUFFICIENT`로 표시한다.

## 고정 구현 체크리스트

아래 순서대로 진행한다. 한 묶음이 끝날 때마다 코드, 데이터, 화면, 운영 통제를 함께 확인한다.

### AI-0. 베타 기준 확정과 데이터 설계

- [ ] 베타 대상 매장과 최소 주문량·최소 기간 기준 결정
- [ ] 첫 베타에서 탐지할 신호를 제한: 주문/매출 변화, 객단가 변화, 메뉴 변화, 취소·품절, 처리 지연
- [ ] 각 신호의 사실 수치, 비교 기준, 데이터 부족 조건 정의
- [ ] AI에 전달할 집계 데이터와 절대 전달하지 않을 개인정보 목록 확정
- [ ] AI 결과 카드의 고정 형식과 점주 승인 문구 확정
- [ ] 잘못된 추천·데이터 부족·한도 초과 등 사전 테스트 사례 작성

**완료 기준:** 무엇을 분석하고 무엇을 분석하지 않는지, 어떤 데이터가 부족하면 침묵하는지가 문서와 테스트 사례로 확정된다.

### AI-0 초기 운영 기준안

아래 값은 첫 베타를 안전하게 시작하기 위한 **초기 기준안**이다. 실제 베타 매장 지정 전 점주와 운영자가 최종 확인한다.

#### 베타 대상 매장

- 첫 베타는 3개 매장으로 시작하고, 안정적이면 최대 5개 매장까지 늘린다.
- 매장은 운영 상태여야 하고 기본 메뉴·주문 설정이 완료되어야 한다.
- 점주가 AI 베타 사용과 피드백 제공에 동의해야 한다.
- 신규 서비스의 첫 베타에는 이전 주문 이력을 참여 조건으로 두지 않는다. 참여 첫날부터 AI Brief의 사실 요약과 데이터 수집 상태를 제공한다.
- OPS는 언제든 매장을 베타에서 제외하거나 AI 기능을 중지할 수 있다.

#### 정식 비교 분석·개선 제안 활성화 기준

- 최소 8주 이상의 주문 이력이 있어야 한다.
- 최근 8주에 취소되지 않은 주문 200건 이상의 주문 기록이 있어야 한다.
- 최근 4주에 영업·주문이 거의 없는 긴 공백이 없어야 한다.
- 메뉴별 분석은 해당 메뉴의 주문이 충분할 때만 한다. 표본이 적으면 메뉴 이름을 넣어 추천하지 않는다.

이 기준은 베타 참여 또는 AI Brief 이용 조건이 아니다. 기준에 못 미쳐도 AI Brief는 제공하며, 개선 제안만 보류한다.

#### 주차별 AI Brief 운영 기준

| 기간 | AI가 보여 주는 내용 | 하지 않는 것 |
| --- | --- | --- |
| 시작~1주 | 오늘의 주문 수·매출·상위 메뉴·취소 건수와 데이터 수집 상태 | 추세 비교, 원인 판단, 개선 제안 |
| 2주차 | 초기 변화 관찰과 규칙으로 확인되는 운영 이상 징후(예: 취소 급증) | 매출 하락 원인 단정, 메뉴·마케팅 변경 제안 |
| 3~7주차 | 반복 패턴 후보와 추가 관찰 필요 여부 | 확정적 진단, 실행 권고 |
| 8주차 이후 및 주문 기준 충족 | 기간 비교, 가설, 하나의 개선 제안과 점주 승인 흐름 | 자동 적용 |

- 주문 이력이 8주를 넘어도 주문 기준을 충족하지 못하면 초기 관찰 단계에 머문다.
- 반대로 시작 직후라도 규칙으로 확실히 확인되는 오류·취소 급증 같은 운영 이상은 알릴 수 있다. 다만 이를 AI의 원인 분석이나 개선 제안으로 표현하지 않는다.
- 원칙은 **데이터가 적을수록 AI가 말하는 범위를 줄인다**는 것이다.

정식 기준을 충족하지 못하면 오류가 아니라 아래처럼 정상 안내한다.

> 아직 비교 분석을 위한 주문 데이터가 충분하지 않습니다. 오늘의 현황을 먼저 확인하고, 데이터가 쌓이면 개선 제안을 시작합니다.

#### 첫 베타에서 분석할 신호

처음에는 이미 주문 데이터로 확인 가능한 신호만 사용한다.

1. 최근 같은 요일 기준 주문 수·매출 변화
2. 객단가 변화
3. 메뉴별 주문 수와 매출 변화
4. 취소 비율 변화

#### 첫 베타에서 보류할 신호

아래는 데이터 이력 또는 별도 기준이 더 필요하므로 첫 베타에 넣지 않는다.

- 주문 처리시간과 시간대별 병목
- 반복 품절 분석
- 메뉴 동반구매·세트 추천
- 계절성 판단
- 가격·쿠폰·포인트 관련 제안

#### 비용을 예측 가능하게 만드는 운영 방식

- 기본 브리핑은 매장별로 아래 세 종류를 모두 제공한다. 같은 종류의 브리핑을 같은 기간에 다시 볼 때는 새 호출 대신 저장된 결과를 보여 준다.
  - **일간 브리핑:** 하루 1회, 월 최대 31회. 오늘의 변화와 즉시 확인할 신호를 짧게 안내한다.
  - **주간 브리핑:** 주 1회. 한 주의 흐름과 실행 제안을 정리한다.
  - **월간 브리핑:** 월 1회. 누적 성과, 반복 문제, 다음 달 운영 방향을 정리한다.
- 같은 날 점주가 다시 볼 때는 새 AI 호출 대신 저장된 결과를 보여준다.
- 점주의 직접 재분석은 초기 베타에서 제공하지 않는다. 재분석 기능은 호출 비용·품질 기준과 함께 별도 도입한다.
- 일간 브리핑과 일반 문의 응답은 비용 중심 모델인 **OpenAI GPT-5.6 Luna**를 사용한다. 주간·월간 브리핑과 복잡한 장애 분석은 품질 중심 모델인 **GPT-5.6 Terra**를 사용한다.
- 일반 문의 AI는 매장별 하루 10회, 월 100회까지 허용한다. 복잡한 장애 분석은 매장별 월 5회까지이며, `master`가 시작할 때만 실행한다.
- 100개 매장 베타에서 일간·주간·월간 브리핑과 베타 초반 문의 최대 200건, 복잡 장애 분석 최대 15건을 함께 고려한 운영 예상 비용은 월 **35~45달러**다. 이는 사전 추정치이며, 실제 첫 달 기록으로 조정한다.
- 플랫폼 전체 월 예산은 **50달러**로 설정한다. 추정 누적 비용이 **40달러**에 도달하면 새 외부 AI 호출을 자동 중지하고, `master`가 검토·재허용하기 전까지 유지한다. 호출 집계 시차나 최종 청구 차이까지 고려한 절대 상한은 50달러다.
- 외부 AI 호출은 AI-1의 서버 전용 API 키·기록·한도 차단이 구현되기 전까지 기본 비활성 상태를 유지한다.

이 방식은 AI가 필요 이상으로 자주 호출되어 비용이 예측하기 어려워지는 것을 막는다.

### AI-1. 안전한 분석·기록 기반

- [ ] AI 분석, 제안, 승인, 실험, 결과 상태를 저장하는 DB 구조 설계
- [ ] 주문 단계별 처리 시각을 남길 필요가 있는지 현재 흐름과 대조해 확정
- [ ] 매장별 집계 데이터를 만드는 서버 전용 조회 기능 구현
- [ ] 매장·점주 권한을 서버에서 다시 확인하는 AI 요청 경로 구현
- [ ] AI 결과를 정해진 형식으로 검증하고 저장
- [ ] AI 호출 실패가 주문·결제·기존 통계를 막지 않도록 분리

**완료 기준:** AI가 직접 DB를 바꾸지 않으며, 모든 분석 결과와 상태 변화가 추적 가능하다.

#### AI-1 설계안: AI에 전달하는 데이터

AI는 주문 원본 DB에 직접 접속하지 않는다. 서버가 매장 권한을 확인한 뒤, 분석에 필요한 기간의 **집계값만** 만들어 전달한다.

| 전달 가능 | 전달하지 않음 |
| --- | --- |
| 날짜별 주문 수·매출·객단가·취소율 | 고객 이름·이메일·전화번호·계정 ID |
| 메뉴별 판매 수량·매출·변화율 | 주문 요청사항·테이블 번호·진동벨 번호 |
| 매장/포장 주문 비율·시간대별 건수 | 결제키·카드/계좌 정보·환불 사유 원문 |
| 데이터 기간·표본 수·분석 가능 상태 | 원본 주문 행 전체와 고객별 주문 이력 |

- 메뉴명은 매장 운영 분석에 꼭 필요한 경우에만 포함한다.
- 분석 입력값과 결과에는 고객 개인정보를 넣지 않는다.
- AI 호출 실패는 주문, 결제, 기존 통계 화면에 영향을 주지 않는다. 해당 분석만 실패 상태로 기록하고 재시도 여부를 OPS가 통제한다.

#### AI-1 설계안: 기록할 7가지 장부

| 장부 | 쉽게 말하면 | 핵심 기록 |
| --- | --- | --- |
| AI 매장 설정 | 이 매장에서 AI를 켜도 되는지 | 베타 참여, 중지 상태, 일/월 한도 |
| AI 한도 규칙 | 플랫폼·매장·점주·기능별 제한 | 사용 허용 여부, 호출·비용 한도 |
| 분석 실행 | 언제 어떤 기간을 분석했는지 | 매장, 요청자, 기간, 데이터 충족 상태, 성공/실패 |
| AI Brief·제안 | AI가 무엇을 말했는지 | 사실, 가설, 신뢰도, 제안 1개, 근거 수치 |
| 점주 결정 | 점주가 제안을 어떻게 처리했는지 | 승인·보류·거절, 처리 시각, 처리한 사람 |
| 사용량·비용 | 호출별 비용과 오류 | 기능, 모델, 토큰/비용, 성공·실패 사유 |
| OPS 제어 이력 | 누가 언제 AI를 멈추거나 풀었는지 | 대상 매장/계정/기능, 사유, 변경 전후 상태 |

분석 실행, 점주 결정, OPS 제어 이력은 수정으로 덮어쓰지 않고 새 기록을 남긴다. 따라서 나중에 “어떤 근거로 무엇을 보여 주었고, 누가 승인했는지”를 추적할 수 있다.

#### AI-1 권한 흐름

```text
점주가 AI Brief 요청
→ 서버가 로그인·매장 소유/관리 권한·AI 사용 가능 상태 확인
→ 서버가 해당 매장의 안전한 집계값만 생성
→ AI가 정해진 형식의 결과를 반환
→ 서버가 형식·한도·매장 일치 여부를 검증하고 기록
→ 점주에게 결과 표시
```

- 브라우저에는 AI 제공사 비밀키나 Supabase 서비스 키를 절대 전달하지 않는다.
- 점주는 본인이 권한을 가진 매장 결과만, OPS는 자신의 OPS 역할에 허용된 운영 화면만 볼 수 있다.
- AI는 매출, 메뉴, 설정을 직접 수정할 수 없고, 점주의 별도 승인 흐름을 통과한 기능만 이후 단계에서 실행할 수 있다.

#### AI-1에서 추가로 확인할 기존 데이터

- 현재 주문 데이터에는 주문 생성 시각, 주문일, 주문 상태, 주문/메뉴 금액·수량이 있어 초기 AI Brief에 필요한 핵심 수치는 만들 수 있다.
- 주문 단계별 처리 시각(확인·제조·포장완료 등)은 현재 분석용 이력으로 충분히 남아 있는지 확인되지 않았다. 첫 베타의 병목·처리시간 분석은 보류하고, 필요성이 확정될 때만 별도 이력을 추가한다.

### AI-2. OPS 사용량·비용 통제

- [ ] 호출마다 매장·점주·기능·사용량·비용·성공 여부 기록
- [ ] 매장별·점주별·플랫폼 전체 일/월 한도 설정
- [ ] 한도 초과 시 자동 차단과 사용자 안내
- [ ] OPS에서 사용량·예상 비용·오류·차단 상태 조회
- [ ] OPS에서 매장·계정·기능별 중지와 재허용
- [ ] 플랫폼 전체 예산 초과 시 신규 AI 호출 중단

**완료 기준:** 운영자는 어느 매장에서 얼마를 썼는지 보고, 필요하면 즉시 사용을 멈출 수 있다.

### AI-3. 점주용 AI Brief와 개선 제안

- [ ] 오늘의 AI 요약 최대 3개 표시
- [ ] 근거 수치, 사실, 추정, 신뢰도, 추천 행동 1개 표시
- [ ] 데이터 부족·정상·추가 관찰 상태 표시
- [ ] 점주가 승인, 보류, 거절을 선택하는 화면
- [ ] 기존 통계 화면으로 바로 이동할 수 있는 연결

**완료 기준:** 점주는 AI의 말을 맹신하지 않고 근거를 확인한 뒤 다음 행동을 선택할 수 있다.

### AI-4. 승인형 실험과 결과 검증

- [ ] 실험의 변경 내용, 기간, 성공 기준, 부작용 지표 기록
- [ ] 실험 시작 전 점주 최종 승인
- [ ] 실험 중지와 되돌리기
- [ ] 결과를 성공, 실패, 추가 관찰로 분류
- [ ] 효과가 확인된 항목만 `STABLE`로 관리
- [ ] `STABLE` 항목과 충돌하는 새 제안 차단

**완료 기준:** AI 제안이 실제 변경으로 이어질 때 누가 무엇을 승인했고 결과가 어땠는지 모두 확인할 수 있다.

### AI-5. 베타 공개 전 검증과 운영 준비

- [ ] 데이터 부족, 잘못된 추천, AI 오류, 시간 초과, 한도 초과, 승인 취소, 실험 실패 테스트
- [ ] 점주 권한·매장 분리·OPS 권한 테스트
- [ ] 개인정보 최소 전달과 로그 보관 기준 점검
- [ ] OPS 비용 한도와 긴급 중지 기능 실제 확인
- [ ] 베타 매장용 안내와 피드백 수집 경로 준비
- [ ] Production 배포 후 제한된 베타 매장으로 최소 운영 확인

**완료 기준:** 문제가 생겨도 주문·결제·매장 운영을 멈추지 않고, OPS가 즉시 파악하고 차단할 수 있다.

아래는 베타 공개 기준에 포함하지 않는다.

- AI 자동 가격 변경

- 자유대화형 AI
- 날씨·상권·경쟁매장 분석

이 항목들은 베타 운영 데이터와 사용 사례를 검토한 뒤 별도 정책으로 결정한다.
