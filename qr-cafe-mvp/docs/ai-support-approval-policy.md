# AI 고객지원·승인형 조치 운영 기준

상태: **초기 정책 확정 · 구현 전 설계 기준**

## 목적

점주 문의를 플랫폼 안에서 접수하고, AI가 조사와 처리안 작성을 돕되 중요한 변경은 사람이 승인한 뒤에만 전용 서버 기능으로 실행한다.

AI는 직접적인 데이터베이스 수정, 결제 취소·환불, 구독 변경, `main` 병합 또는 Production 배포 권한을 갖지 않는다.

## 초기 문의 흐름

```text
점주 문의
→ AI 분류·추가 질문·허용된 매장 상태 조회
→ 답변 또는 OPS 조치안
→ 승인 필요 조치라면 OPS 승인함
→ 승인 후 서버 재검증·실행
→ 문의 이력에 결과 기록
```

점주가 직접 처리할 수 있는 사용법·설정 문제는 AI가 방법과 해당 화면의 바로가기를 안내한다. AI가 불필요하게 실행 권한을 대신 사용하지 않는다.

## 점주 문의 화면과 자동 이관 기준

- 기존 지원센터 티켓의 매장 연결, 문의 번호, 처리 상태, 환불 요청 연결과 OPS 이력은 유지한다.
- 점주가 새 문의를 접수할 때는 제목과 우선순위를 직접 입력하지 않는다. `사용·설정 도움`, `결제·구독 문의`, `오류 신고` 중 가까운 맥락 하나만 선택하고 자유롭게 내용을 작성한다.
- 선택한 맥락은 AI의 초기 힌트일 뿐이며, AI와 서버가 실제 내용을 기준으로 내부 분류·위험도·우선순위를 다시 판단한다.
- 오류 신고에는 오류 문구와 화면 캡처를 선택적으로 추가할 수 있다.
- 문의 상세는 점주, AI, OPS의 안내와 처리 결과가 시간순으로 쌓이는 처리 이력으로 제공한다. 초기에는 실시간 상담 채팅을 만들지 않는다.

| 상황 | 초기 처리 방식 |
| --- | --- |
| 사용법·일반 설정 | AI가 즉시 방법을 안내한다. |
| 권한이 확인된 매장 상태 조회 | 서버의 읽기 전용 확인 결과를 바탕으로 맞춤 안내한다. |
| 정보가 부족하거나 모호함 | AI가 필요한 정보만 추가 질문한다. |
| 결제·환불·구독 변경 | 자동 실행하지 않고 OPS 검토 또는 승인함으로 보낸다. |
| 개인정보·계정·사업자 인증 | 자동 판단하지 않고 OPS로 이관한다. |
| 주문 불가·결제 실패·오류 화면 등 장애 의심 | 오류 근거를 모아 Incident 후보로 이관한다. |
| AI가 확신하지 못함 | 추측하지 않고 OPS 확인으로 이관한다. |

점주 화면에는 내부 카테고리, 모델명, 위험도 대신 `AI 안내 준비`, `추가 정보 필요`, `운영팀 확인 중`, `승인 처리 대기`, `처리 완료`처럼 이해하기 쉬운 상태만 표시한다.

## 구독 환불

- 결제 후 10분 이내의 전액 취소는 기존 점주 직접 취소 흐름을 유지한다.
- 10분 이후의 중도해지·환불은 플랫폼에서 검토 요청을 접수한다.
- AI는 결제, 실제 결제금액, 미사용 기간, 할인·크레딧, 기존 환불·분쟁 여부를 조사해 처리안을 작성한다.
- 환불 예정액은 AI가 아니라 고정된 서버 계산 엔진이 계산한다.
- 초기 베타에서는 `master`만 실제 환불·기간 연장 처리를 승인할 수 있다.
- 승인 직전과 실행 직전에 서버가 결제 상태, 중복 환불, 대상 매장, 금액을 다시 확인한다.
- 환불 완료 시 신규 주문 접수 등 구독 기능은 즉시 제한한다. 로그인, 결제·환불 내역 확인, 이미 접수된 주문 처리는 계속 허용한다.
- 플랫폼 귀책 또는 중복결제는 점주가 환불 또는 기간 연장 중 선택할 수 있다.
- 매장의 고객 주문 전체·부분 환불은 이 초기 승인형 자동화 범위에 포함하지 않는다.

## 시스템 장애와 코드·DB 수정

```text
장애 문의 또는 OPS Incident
→ AI가 근거·영향 범위·수정 방안 작성
→ 1차 승인: 격리된 작업공간에서 수정안 준비
→ branch 생성·코드 수정·테스트·Preview
→ 변경 파일·검증 결과 보고
→ 2차 승인: PR 병합 또는 Production DB 적용
```

- 1차 승인은 수정안을 준비하는 권한일 뿐, 라이브 반영 권한이 아니다.
- 코드 수정은 별도 branch와 Preview에서 검증한다.
- DB 변경은 migration 초안과 영향 분석을 먼저 만들고, Production 적용은 별도 승인으로만 수행한다.
- AI는 코드·DB를 임의로 수정하거나 Production에 직접 반영하지 않는다.

## 오류 캡처와 첨부 파일

- 점주는 문의에 PNG, JPG, WEBP 형식의 오류 캡처 또는 사진을 최대 3개까지 첨부할 수 있다.
- 파일당 최대 크기는 5MB이며, 오류 문구는 별도 입력란에 최대 2,000자까지 작성할 수 있다.
- 초기에는 PDF를 받지 않고, 첨부 이미지를 외부 AI에 전달하거나 이미지 자체를 AI로 분석하지 않는다.
- 업로드 전 카드번호, 계좌번호, 비밀번호, 고객 전화번호·주소 등 개인정보를 가린 뒤 첨부하도록 명확히 안내한다.
- 첨부 파일은 공개 URL을 만들지 않는다. 문의 매장과 권한 있는 OPS만 제한된 방식으로 확인한다.
- 문의가 종료된 날부터 90일이 지나면 원본 첨부 파일을 삭제한다. 장애 유형과 처리 결과 같은 비식별 운영 이력은 별도 기준으로 보관할 수 있다.
- 보관 기간과 법적 고지 문구는 외부 법률 검토 뒤 최종 조정한다.

## OPS 승인 권한

- 초기 베타는 사용자님의 `master` 계정 한 개만 실제 승인자로 운영한다.
- `master`는 모든 문의 확인, 환불·기간 연장 승인, AI 중지, 수정안 준비 승인을 수행할 수 있다.
- 코드의 `main` 병합과 Production DB 적용은 `master`의 별도 최종 승인 없이는 진행하지 않는다.
- `billing`, `support`, `viewer`는 현재 추가 계정을 만들기 위한 조건이 아니다. 향후 직원이나 공동 운영자가 생길 때 필요한 범위만 분리하기 위한 역할 기준이다.
- `billing`은 결제·구독 문의 검토와 조치안 작성, `support`는 문의 답변·추가 정보 요청·Incident 작성, `viewer`는 현황 조회만 담당한다. 이 역할들은 금전·구독·권한 변경을 승인할 수 없다.
- AI는 사용자 계정이나 OPS 역할을 갖지 않는다. AI는 조사, 답변 초안, 조치안 작성까지만 수행한다.

## AI 제공사·사용량·비용 기준

- OpenAI API 프로젝트의 소유자는 리온오더 운영 전용 이메일 계정으로 둔다. 개인 OpenAI 계정이나 개발자 개인 이메일에 서비스 소유권을 두지 않는다.
- 초기 베타 결제수단은 개인 카드를 사용할 수 있다. 사업용 계좌·카드가 준비되면 API 프로젝트의 결제수단만 사업용 카드로 교체하고, 초기 결제 영수증과 사용 내역은 서비스 준비 비용 근거로 보관한다.
- 초기 제공사는 **OpenAI API** 한 곳으로 시작한다. 제공사·모델 이름은 소스 코드에 고정하지 않고 서버 운영 설정으로 관리한다.
- 일반 문의의 분류·추가 질문·안내는 **GPT-5.6 Luna**를 사용한다. 결제·환불·개인정보·권한·사업자 인증·확신 부족 사례는 자동 실행하지 않고 OPS로 이관한다.
- 복잡 장애의 근거 정리와 수정안 초안은 **GPT-5.6 Terra**를 사용하며, `master`가 장애 분석을 시작할 때만 호출한다.
- 일반 문의 AI는 매장별 하루 10회, 월 100회까지 허용한다. 복잡 장애 분석은 매장별 월 5회까지 허용한다.
- 플랫폼 전체 월 예산은 50달러다. 추정 누적 비용이 40달러에 도달하면 신규 외부 AI 호출을 자동 중지하고 `master` 검토 전까지 유지한다.
- 100개 매장 베타의 초반 문의량은 월 100~200건, 복잡 장애 분석은 월 5~15건까지를 운영 안전 기준으로 본다. 이는 업계 평균이 아니라 리온오더의 초기 관측 전 보수적 계획값이며, 첫 달 운영 기록으로 재조정한다.
- 외부 AI 호출은 서버 전용 키, 호출별 사용량·예상 비용 기록, 한도 차단이 구현되기 전까지 비활성 상태다.
